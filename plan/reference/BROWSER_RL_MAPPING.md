> 每节末尾标注验证状态：✅ 已实测 / 🔶 部分实测（含推断）/ ⬜ 待实测。

## 0. 结论速览

1. **网页版完全可以作为 RL 环境**：游戏状态以稳定的 CSS 类（`ccbs-*`）完整编码在 DOM 中；
   每类动作对应固定的 1–3 步点击序列；奖励可由分数面板差分得到。✅
2. **动作层面推荐用"结构化动作"而不是平铺 `ALL_ACTIONS` 索引**：
   网页交互天然是分层的（模式按钮 → 目标元素 → 确认/支付方式选择），
   合法动作掩码可直接从 DOM 可交互元素推导，比仓库的 `Discrete(len(ALL_ACTIONS))`（上千维组合枚举）更适合浏览器层（§4.2）。✅
3. **对手预定卡表面是隐藏信息，但对完整记忆的观察者基本是公开的**：预定明牌可由桌面 diff 还原身份、
   购买时刻会公开揭示卡面；只有"从牌库预定"的卡在揭示前是真实隐变量——而其信念分布
   （该 tier 未见面孔上的均匀分布）可由记忆精确计算（§3.2）。
   配合事件流记忆模块，浏览器层观测可与仓库完美信息引擎 `SplendorGameRule` 基本对齐。🔶
4. **两侧牌库完全一致**：引擎与网页版均为每层 36/26/16（共 78 张）发展卡、初始 noble 需求结构相同，
   且 `(tier, colour, points, cost)` 四元组在 78 张卡上零重复——卡面身份无需图片映射表，直接查表即可（§3.1）。✅

## 2. 会话管理：房间、身份与自对弈双开配方

网页版身份 = cookie `gid`（服务器首访分配）+ `localStorage.user.emoji`（可选微信/QQ 登录）。

1. 大厅 `https://game.hullqin.cn/ccbs` → `创建房间`（进入 `/ccbs/gtNN`）。
2. 点座位 1 的 `加入` 入座（成为房主），`修改人数` 可选 2/3/4 人。
3. **开始游戏需要 ≥2 名玩家**。ego-browser 的多个任务空间共享 cookie jar（同一身份），
   双开两个身份的方法（实测有效）：
   - 空间 A：写入 gid-A cookie → 载入房间 → 入座位 1；
   - 空间 B：`Network.deleteCookies(gid)` → 服务器分配新 gid-B → 载入房间 → 入座位 2；
     （注意：此后 jar 中是 gid-B，空间 A 的页面要在**换 cookie 之前**先完成载入，其 ws 连接身份在握手时固定）
   - 回空间 A 点 `开始游戏`。
4. 每个浏览器标签页同一身份只能有**一条**房间连接，重复载入会提示"你已在新的浏览器窗口进入该房间"。
5. 可选 `无操作计时 / 有操作计时`——若开启计时，agent 的决策延迟必须小于限时。

验证状态：✅ 已实测（含"cookie 域残留导致双 gid"坑：换身份前须对 `game.hullqin.cn` 与 `.game.hullqin.cn` 两个域都 `deleteCookies`）。

## 3. 观测（Observation）

### 3.1 DOM 抽取 schema

颜色编码（面板宝石已交叉验证）：`ccbs-color-0..5 = 白 / 蓝 / 绿 / 红 / 黑 / 金`。
卡色编码：`ccbs-type-0..4` 同上（`ccbs-type-5` 仅用于牌库背/卡背）。

| 游戏对象 | 选择器 / 读取方式 |
|---|---|
| 三层明牌区 | 3 个 `div.flex.justify-center.origin-top`（行序 = tier 3/2/1）；每行第 1 个 wrapper 是牌库 |
| 牌库剩余 | `.ccbs-card.ccbs-type-5 .ccbs-left-count` 文本（实测 36→35→34 递减正确） |
| 发展卡 | `.ccbs-card.ccbs-type-{色}.ccbs-img-{i}`；分数 `.ccbs-score`；费用为子元素 `.ccbs-circle.ccbs-color-{c}` 的文本 |
| 卡的唯一身份 | `(tier, colour, points, cost)` 四元组在全部 78 张卡中**零重复**（已用引擎逐卡验证），无需依赖 `ccbs-img` 美术编号 |
| 贵族 | `.ccbs-noble.ccbs-noble-{id}`；分数 `.ccbs-score`（3）；需求 `.ccbs-rect.ccbs-color-{c}` 文本 |
| 公共宝石供给 | `button.ccbs-circle.ccbs-color-{c}`（我方回合可点；非我方回合渲染为 div）文本 = 数量 |
| 玩家面板（每座位） | emoji + 座位号 + `N分` + 5 个 `.ccbs-rect.ccbs-color-{c}`（永续卡数）+ 6 个 `.ccbs-circle.ccbs-color-{c}`（手中宝石数）+ 预定卡背 `.ccbs-card.ccbs-type-5.ccbs-img-{tier}` |
| 自己的预定区 | 灰带 `div.flex.justify-center.origin-top.bg-gray-400` 中的**明牌** `.ccbs-card` |
| 对手的预定区 | 仅 `.ccbs-card.ccbs-type-5` **卡背**；卡背 `ccbs-img-{i}` 泄露 tier（i=0/1/2）。卡面身份靠**记忆重建**恢复（§3.2） |
| 回合状态 | 页面文本 `等待你操作` / `等待玩家{座位号}操作` |
| 顶层操作按钮 | `💎取宝石`、`💰购买发展卡`、`💳预定发展卡`、`❌放弃`（仅我方回合可点） |
| 确认条 | 灰条 `div.mt-2.p-2.bg-gray-400` 内 `确认拿这些` / `取消` |

验证状态：✅ 已实测（全部选择器在 2 人局中逐项读取并与操作结果交叉验证）。

### 3.2 信息集与记忆重建：隐藏信息的还原

网页版虽然把对手预定卡渲染成卡背，但对**有完整记忆的观察者**而言，大部分预定信息是公开的：

| 事件 | 表面可见 | 记忆重建后的信息 |
|---|---|---|
| 对手预定**明牌** | 该桌面位置被换新牌（前后 DOM diff）+ 对手面板 +1 金 | **卡面身份完全可得**：换掉的那张卡就是被预定的卡 |
| 对手**从牌库预定** | 对应 tier 牌库计数 -1、对手面板 +1 金、卡背 tier | 卡面身份不可得，是真实隐变量；但 tier 已知（卡背泄露） |
| 对手**购买预定卡** | 购买瞬态展示卡面（约 1–2s）+ 面板产量颜色 +1、分数 +N | **身份在购买时刻公开揭示**，记忆即时补全 |

因此：

1. **预定明牌 ≈ 公开信息**：agent 只要维护"桌面快照 + 事件流"，对手从桌面预定走的卡可直接以真实卡向量填入特征，
   与仓库完美信息引擎的假设一致。
2. **从牌库预定 = 可精确计算的信念分布**：78 张卡列表固定，且所有已见卡（桌面明牌、双方预定、历史购买揭示）
   都在记忆里、牌库剩余数可见（`ccbs-left-count`），所以该隐变量的分布就是
   "该 tier 未见面孔上的均匀分布"（多张同 tier 卡背则不放回），**无需近似推断**。
   特征可用该分布的期望（逐色 cost/points 期望）或保留分布采样。
3. **工程要求——事件流而非慢轮询**：购买揭示是瞬态弹窗，0.5s 轮询快照可能错过；
   记忆模块应基于 DOM `MutationObserver`（或旁听 ws 帧）增量更新，
   并把"对手面板 +1 金 / 牌库计数 -1 / 桌面槽位换新"作为预定事件的可靠交叉验证信号
   （即使错过瞬态弹窗，产量颜色 +1 与分数 +N 也能在剩余未见卡集合中唯一锁定多数卡面）。

验证状态：🔶 推断 + 局部实测（三类事件的表面可见部分均已实测；记忆重建算法本身待实现后验证）。

### 3.3 对齐仓库特征向量

对应到仓库特征向量（`features.py`）的抽取方式：

- `metrics` 段：`agent.score` ← 面板 `N分`；`gems` ← 自己面板 6 个 circle；`cards per color` ← 5 个 rect；
  `turns count` ← 自行计数；对手分数 ← 对手面板；`distances`（到各卡/贵族的距离）由桌面卡面 + 自己 buying power 计算，算法与仓库一致。
- `cards` 段（15 × 13）：桌面 12 张明牌 + 自己预定区明牌，逐卡 `onehot(color) + cost + deck_id + points`；
  对手预定卡槽位按 §3.2 的记忆重建填写（已还原身份 → 真实卡向量；仅知来自牌库 → 信念期望值）。

验证状态：🔶 schema 已实测；到特征向量的转换代码待实现。

## 4. 动作（Action）

### 4.1 各类动作的点击序列（实测）

#### A. `COLLECT_SAME` / `COLLECT_DIFF`（取宝石）
1. click `💎取宝石`（进入选择模式，提示"拿2个相同或3个不同宝石"）；
2. click 供给筹码：同色 2 个（要求该色供给 ≥4）或 3 个不同色（各 1 个）；
3. click `确认拿这些`（`取消` = 清空重选）。

对应仓库：`{type: collect_same|collect_diff, collected_gems, returned_gems}`。
**超过 10 颗上限时的返还子步骤未实测**（仓库对应 `returned_gems ≠ ∅` 的动作；预测网页会再让玩家点筹码选返还并确认）。

#### B. `RESERVE`（预定）
1. click `💳预定发展卡`（提示"请从银行选择1个发展卡预定"，所有卡含牌库堆出现"预定"覆盖按钮）；
2. click 目标卡的 `预定` 按钮；
3. 自动获得 1 金（即仓库 `collected_gems={yellow:1}`）。

#### C. `BUY_AVAILABLE` / `BUY_RESERVE`（购买，含多支付方式）
1. click `💰购买发展卡`；
2. 所有**可负担**的卡（含自己预定区）自动渲染 `购买` 覆盖按钮，并直接给出一种支付方案提示
   （`花费1白1蓝1红1金`…）；不可负担的卡显示 `缺X`；
3. click `购买`：
   - 支付方式唯一 → **立即成交**；
   - 多种支付方式 → 底部出现选择器"请选择支付方式"，以药丸按钮列出（实测出现 `3白` 与 `2白1金`），
     **click 药丸即成交**。
4. 成交后：卡离开桌面、补牌（牌库 -1）、产量/分数更新、回合切换。

对应仓库：`{type: buy_available|buy_reserve, card, returned_gems}`。
**注意粒度差异**：仓库的 `build_action` 对 BUY 一律 `returned_gems = card.cost`（引擎自动扣钱），
把"用哪种方式付金"折叠掉了；网页版把支付方式暴露为显式子选择。
留下的"零钱颜色"会影响后续状态（gold 留存 vs 彩色宝石留存不等价），
**浏览器层 RL 的动作空间必须包含支付方式维度**（多支付时等于把 1 个仓库动作拆成 k 个，见 §4.2）。
买预定卡走同一流程（预定区卡片同样出现 `购买` 覆盖按钮）。

#### D. `PASS`（放弃，实测）
1. click `❌放弃` → 弹窗"确认放弃本回合操作吗？"；
2. click `确认放弃` → 回合结束。

#### E. 贵族选择（未实测，官方公告确认存在）
"同时满足多个贵族时，可以选"——对应仓库动作里的 `noble_index` 维度。
浏览器层应在满足条件时枚举该 UI 的选项；仓库引擎在 `applyAction` 中按 `action["noble"]` 处理（+3 分）。

验证状态：A/C/D ✅ 已实测；B ✅ 已实测（金 +1、牌库递减、对手视角牌背）；E ⬜ 待实测。

### 4.2 浏览器层结构化动作空间

```
z1 ∈ {take, reserve, buy, pass}            # 4 个模式按钮
z2 ∈ targets(z1)                            # DOM 枚举：筹码颜色 / 卡 wrapper（含牌库堆/预定区）
z3 ∈ {confirm} ∪ payment_pills ∪ nobles     # 确认 / 支付方式 / 贵族选择
```

合法掩码 = `targets()` 的存在性（例如只有出现 `购买` 覆盖按钮的卡才是合法 buy 目标），
完全由 DOM 推导，无需在浏览器侧重算游戏规则。

训练侧若要复用仓库 PPO 网络（输入 `METRICS_WITH_CARDS_SIZE` 维、输出 `Discrete(len(ALL_ACTIONS))`），
可在 adapter 里做双向翻译：结构化动作 ↔ `ALL_ACTIONS` 索引
（`Action.to_action_element` / `build_action` 已提供该转换）；
多支付方式可在索引外附加一个小的头（k 选 1）。

验证状态：🔶 设计方案（依据 §4.1 实测交互流）。

### 4.3 与仓库 ALL_ACTIONS 的一一对应表

| 仓库动作（`ActionEnum` + 字段） | 网页点击序列 | 备注 |
|---|---|---|
| `PASS` | 放弃 → 确认放弃 | 2 步 |
| `COLLECT_SAME {c:2}`（供给 ≥4） | 取宝石 → 点 c×2 → 确认 | 3 步 |
| `COLLECT_DIFF {c1,c2,c3}` | 取宝石 → 点 3 色 → 确认 | 3 步 |
| `COLLECT_*` + `returned_gems`（>10 返还） | 取宝石 → 选择 → 确认 →（返还子流程，待实测） | 建议先在动作空间禁用"取完必超 10"的选择（网页大概率也不允许这样取） |

## 5. 奖励与终局（Reward & Termination）

### 5.1 即时奖励

- **仓库机制**：`SplendorGameRule.applyAction` 把每个动作的得分增量记入 `agent_trace.action_reward`
  （买卡 +`card.points`、 noble +3）；`generatePredecessor` 回滚时对称取负。
- **网页对应**：面板"N分"文本差分。已实测：买卡得分、贵族 +3 会即时反映在面板。
- 取宝石 / 预定 / 放弃 得分为 0（面板不变），天然是稀疏动作。

### 5.2 回合轮转与"一次 step"的边界

- 状态文本 `等待你操作` ↔ `等待玩家N操作`（已实测，与 `env.step()` 内部模拟对手回合的语义一致）。
- `BrowserSplendorEnv.step()` 应阻塞到再次轮到己方（对手的全部子步骤——含多支付选择、>10 返还——都在其中完成），
  期间持续运行记忆模块事件流（§3.2）。

### 5.3 终局条件

- **引擎侧**：有人 ≥15 分且本轮所有人行动完毕；或死局；或 `ROUNDS_LIMIT=100` 轮。
- **网页侧**：终局结算 DOM 特征待采样（§8），候选信号：分数面板 ≥15 + 状态文本变化 +
  顶部"结束游戏"按钮区文本变化。

### 5.4 训练奖励设计建议

- **稀疏终局奖励**：胜负 ±1（或终局分数差），以"我方视角"定义。

  可选 potential-based shaping，势函数直接用仓库 `features.py` 已有的 normalized 距离指标
  （到各卡 gems/turns 距离、noble 距离），无需另造特征。

```python
    def reset(self, *, seats=2):

        return self.observe(), {"my_turn": self.my_seat}

        #   对手预定槽位：已还原身份 → 真实卡向量；来自牌库 → 信念期望（该 tier 未见面孔均匀分布）
        # 可选：再走 features.extract_metrics_with_cards(...) 对齐仓库观测维度（§3.3）
        ...

    def legal_actions(self):
        # 由 DOM 交互元素推导 §4.2 的结构化动作集合（含支付方式、贵族选项）
        ...

    def step(self, action):
        self._execute(action)              # §4.1 点击序列
        while not self._my_turn_and_settled():
            if self._game_over(): break    # 轮询状态文本 + 分数变化（对手回合内完成对手的全部子步骤）
        reward = self._score_delta(self.my_seat)   # 面板 "N分" 差分（§5.1）= 仓库 action_reward

```

- 等待机制：0.3–0.5s 轮询状态文本（或 `MutationObserver` 计数），配合计时上限做超时保护；
  **记忆更新必须走事件流**（`MutationObserver` 增量 diff 或旁听 ws 帧），慢轮询快照会错过瞬态的购买揭示（§3.2）。
- 自对弈：两个 ego-browser 任务空间各跑一个 env 实例（座位 1/2），cookie 配方见 §2；
  也可让对面座位挂机（真人/随机脚本）只训练己方。
- **可选快通道**：页面与服务器通过 WebSocket 传二进制 protobuf 帧（实测，帧内含完整状态）。
  Hook `window.WebSocket` + `TextDecoder` 即可旁听；若从 HullQin 的开源框架拿到 `.proto`，
  可实现"状态直接读帧、动作直接发帧"，绕过 DOM 与点击。
  但这偏离"浏览器层面"的初衷，且服务器可能校验非法帧，建议作为调试/加速选项而非主路径。

## 7. 关键差异与风险清单

1. **隐藏信息（大部分可通过记忆重建消除，见 §3.2）**：对手预定明牌的身份可由桌面 diff 还原，
   购买时刻会公开揭示；仅"从牌库预定"的卡在揭示前不可知，但可用精确信念分布编码。
   剩余差异：仓库引擎自训时 agent 直接读引擎状态（天然含牌库预定的真实身份），
   部署到网页时该位置只有信念——可用"以信念期望替代真实卡向量"做训练侧增强（随机扰动该槽位），减小落差。
2. **支付方式选择**改变后续状态（零钱颜色不同），动作空间需显式包含（见 §4.1-C、§4.2）。
3. **>10 宝石返还**是额外子步骤（待实测补全 §4.1-A）。
4. **卡面身份**：已验证 `(tier, colour, points, cost)` 在 78 张卡上零重复（§3.1），无需 `ccbs-img` 映射表；
   实现时注意网页 tier 行序（上→下 = 2/1/0）与引擎 `deck_id` 的方向转换。
5. **终局 DOM 特征**待采样（一次 15 分对局即可补全 §5.3；另注意网页有"无操作计时"，agent 循环要限时）。
6. **礼仪/公平**：建议始终自建房间双开自对弈，不要进真实玩家房间跑训练；点击频率保持人类量级。
7. 2 人局 noble 3 张（仓库 `MAX_NOBLES=5` 兼容，特征段按 5 位补零）。
