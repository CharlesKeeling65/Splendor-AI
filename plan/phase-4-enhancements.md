# Phase 4 · 高保真与增强（可选）

> **定位**：按 P3 落差归因结果**决定取舍**的升级项集合。所有接口已在 P0 协议中预留（`step(payment=...)` / `get_payment_options()`），本阶段不破坏任何既有代码。
> **原则**：做与不做、先后顺序由 P3 的数据说话，不凭直觉预先全做。
> **估时**：每项独立，合计 2+ 周（全做的情形）。

## 1. 阶段目标

消除已量化的 sim-to-real 落差来源，并把 agent 水平从"超越程序化 baseline"推向"对抗人类"。

## 2. 升级项清单（各自独立触发）

| ID | 升级项 | 触发条件（来自 P3 归因） | 估时 |
|---|---|---|---|
| T4.1 | 支付方式 tier-2 | 贪心支付造成明显对局劣势（留金局面的失分可量化） | 1~1.5 周 |
| T4.2 | features-v2（供给维度） | 出现"看不见宝石池"导致的失误模式（供给枯竭仍囤该色） | 3~5d + 重训 |
| T4.3 | 记忆重建模块 | 需要对手建模或更高水平（基线特征不需要，见裁决 §1.2） | 1 周 |
| T4.4 | 网页自博弈常态化 | 需要逼近人类水平，回流数据成为常规训练成分 | 3~5d |
| T4.5 | ws protobuf 快通道 | 仅调试/加速需求（非主路径） | 视 schema 而定 |

## 3. 代码改动详解（说明 / 意义 / 原因）

### 3.1 T4.1 支付方式 tier-2：`PaymentEnumeratingGameRule` + `PaymentHead`

**内容**：(a) 引擎侧新子类 `PaymentEnumeratingGameRule(SplendorGameRule)`，覆写买卡动作生成——对每张可买卡枚举全部合法支付（逐色用量 `k_c ∈ [max(0, cost_c − 黄金), min(cost_c, 可用_c)]` 的笛卡尔积，受黄金总量约束），每组合一个合法动作；**默认 `SplendorGameRule` 行为零变化**。(b) 网络侧 `PaymentHead`：输入 trunk 隐层特征 + 所选 buy 动作的卡编码，输出 K=32 维支付 Q 值，掩码来自 `env.get_payment_options(action)`，仅当 `len(options) > 1` 时参与决策。(c) replay 的 transition 增 `payment` 字段；对手侧支付策略随机化。

**意义**：消除两侧唯一硬语义差距（roadmap §1.3），策略获得"留金"这类支付智慧——黄金是通配，留金通常更灵活，贪心付彩色宝石在长期策略上是次优的。

**原因**：(a) **因子化设计（主头 3510 + 支付头 K）而非扩平铺动作空间**：支付组合会让 ALL_ACTIONS 从 3510 爆炸到数万，且破坏所有既有 checkpoint 与 PPO 兼容；辅助头只在多支付时激活，训练成本增量极小；(b) 引擎侧用**子类而非改默认类**：支付枚举会让合法动作数显著增加（拖慢 `getLegalActions`），只在高保真训练/部署时启用，默认路径（PPO、minimax、既有评测）零影响；(c) 对手支付随机化：不随机则对手永远贪心付钱，策略会过拟合"对手永远不留金"的世界观。

**自动验收**：消融实验 tier-2 ≥ tier-1（本地 + 网页双战场，3 seed，差异显著性检验）。
**人工验收**：多支付局面的行为定性审查（是否体现留金偏好）；P3 数据的 go/no-go 评审前置（落差归因显示支付差异贡献小时**不做**此项）。

### 3.2 T4.2 features-v2：公共宝石供给维度

**内容**：特征向量加 5 维供给量（`board.gems` 各色），新建 observation 空间版本（265 → 270），`features-v2` 与既有 265 断开兼容。

**意义**：修复源码裁决 §1.5 发现的**特征盲区**——当前策略完全看不见公共宝石池余量：`collect_same` 需要供给 ≥4、对手锁资源会抽干某色、终局囤宝石要看池子深浅；这些前瞻规划目前全部失明（合法性有掩码兜底，规划没有）。

**原因**：(a) 这是最可能的天花板来源之一，但**必须由失误证据触发而非直觉**：加维度 = 重训 = 与 PPO 的 265 断开兼容，成本高昂；P1 的人工验收 M1.5（反直觉行为登记）正是为这一步收集证据；(b) 供给信息在两侧都现成可得（本地 `board.gems`、网页 supply 按钮），实现成本极低，决策成本才是主体。

**自动验收**：新特征下 M1–M3 门槛全部重跑达标；供给敏感场景的行为回归测试（供给 <4 时不再规划 collect_same 该色）。
**人工验收**：供给敏感对局审查（枯竭色囤积失误消失）；与 v1 checkpoint 的 A/B 对比观战。

### 3.3 T4.3 记忆重建模块 `browser/memory.py`

**内容**：`MutationObserver` 事件流 + 已见卡集合 + 牌库剩余信念（"该 tier 未见面孔上的均匀分布"，BROWSER §3.2）；产出对手预留卡的期望向量（供特征升级用）。

**意义**：把"对手从牌库预定了什么"从完全未知变成**可精确计算的信念分布**——78 张卡清单固定、已见卡全在记忆、剩余数可见，信念无需近似推断。

**原因**：(a) **基线特征不需要它**（裁决 §1.2：265 维只用自己的预留牌）——所以它不在关键路径，只有做对手建模/特征升级时才有价值，这是它被归入 P4 的原因；(b) **必须走事件流而非轮询**：对手购买预留卡的卡面揭示是 1~2s 瞬态弹窗，0.4s 轮询快照会漏；`MutationObserver` 增量更新是唯一可靠方式（BROWSER §3.2 的工程结论）；(c) 信念的正确性可以离线验证：用引擎模拟全信息对局，对比记忆模块（只喂可见投影）算出的信念与真实牌库的 KL 散度。

**自动验收**：信念分布与真实牌库的 KL 散度收敛性测试（引擎模拟 N 局）。
**人工验收**：瞬态弹窗捕获率实测（网页上跑 20 局统计漏检率）。

### 3.4 T4.4 网页双开自博弈 + 回流常态化

**内容**：双身份配方（`session.switch_identity`）+ 两侧各一个 `BrowserSplendorEnv` + 共享本地 replay；采集-训练交替循环。

**意义**：把 P3.3 验证过的回流通路变成常规训练成分——真实环境数据持续修正分布偏移。

**原因**：(a) 自博弈两侧共享同一 replay 是 off-policy 的红利延续（对手视角的经验同样有价值，特征本身是视角化的）；(b) 网页双开**只在自己建的房间**进行，礼仪风险最低；(c) 采样慢（分钟级一局）决定了它是"调味料"而非"主食"——本地混合对手仍是训练主体。

**自动验收**：100 局自博弈数据入库；微调后 vs 人类胜率变化报告产出。
**人工验收**：双开会话稳定性观察（掉线率、身份互串检查——双域 cookie 坑的回归验证）。

### 3.5 T4.5 ws protobuf 快通道

**内容**：Hook `window.WebSocket` + 帧解析（需 HullQin 开源框架的 `.proto`），状态直读帧、动作直发帧。

**意义**：绕过 DOM 与点击的延迟与脆弱性，单步成本降一个量级。

**原因**：**定位为调试/加速选项而非主路径**（BROWSER §6 已明确）——(a) 偏离"浏览器层面"的项目初衷；(b) 服务器可能校验非法帧，直发动作有封号风险；(c) DOM 路径的价值恰在于它只使用人类可用的接口。仅当 DOM 路径的延迟成为回流数据量的硬瓶颈时才考虑。

**人工验收**：与 DOM 路径的行为一致性抽检（同局面两条路径的观测应一致）；风险评估（服务器条款审查）后才能启用。
