## M0.2 掩码构建吞吐对比（2026-09-05，本机 Apple Silicon / Python 3.13）

对比对象：`create_legal_actions_mask` + `create_action_mapping` 改造前（`_slow_*`，O(3510) 线性扫描）
与改造后（ACTION_INDEX 缓存，O(1) 查表）。样本状态含 24 个合法动作，各重复 20 次取均值：

| 实现 | 掩码构建 | 映射构建 | 合计/步 |
|---|---|---|---|
| 旧（线性扫描） | 2.298 ms | 2.272 ms | 4.570 ms |
| 新（缓存查表） | 0.032 ms | 0.029 ms | 0.061 ms |
| **提速** | ×72.0 | ×78.9 | **×75.3** |

结论：达到"≥50× 掩码构建提速"的验收线。训练路径每步两次调用（step 内 mapping + mask），
1×10⁶ 步训练可节省约 75 分钟纯索引开销（单核估算）。

## 规则实测结论速览

| # | 实验 | 结论 | 与引擎一致性 |
|---|---|---|---|
| E1 | 多贵族选择 | 🔶 官方公告确认功能存在（2026/8/30 更新："同时满足多个贵族时，可以选"）；具体 UI 待 P3 实战补测 | 待定 |
| E2 | >10 宝石返还 | ✅ 见下文；**允许丢弃刚拿的颜色** | **不一致（网页更宽松）** |
| E3 | 终局 DOM | 🔶 强退路径已实测；自然终局（15 分）结算画面待 P3 补测 | 部分 |
| E4 | 空牌库 reserve | ⬜ 单局不可达（牌库 36/26/16 过深，无法清空一整层） | 待定 |
| E5 | 自愿少拿宝石 | ✅ **网页允许只拿 1 颗** | **不一致（网页=标准规则，引擎更严）** |
| E6 | 同色 7 张上限 | ⬜ 单局不可达（同色 7 张需专门构造） | 待定 |

**总体裁决**：两处已确认差异方向一致——**引擎合法动作集 ⊆ 网页可执行动作集**（引擎更严格）。
因此"掩码走引擎规则"的设计安全：agent 在引擎掩码内选动作，在网页上**永远可执行**；
代价是放弃了网页允许的少量边角机会（少拿宝石、丢刚拿色），策略价值不会被系统性破坏。
详细取舍见下方 ADR。

## E1 多贵族选择 UI（决定 action_executor 贵族分支）✅（2026-09-11 bundle 复核补全，见下）

- **判定问题**：一回合同时满足多个贵族时，网页如何呈现选择？能否不选？
- **实测/佐证**：大厅公告（2026/8/30 更新）原文：*"同时满足多个贵族时，可以选。有多种方式购买发展卡时，可以选。增加计时功能。"*——功能官方确认存在，但本次会话未能自然构造出双贵族同满的局面。
- **结论**：功能确认存在；**具体选择器与判定时机已由 2026-09-11 的 bundle 复核补齐**（见文末「ccbs bundle 复核」§新增事实）；
  P3 实战首遇时仅需确认"网页行为与 bundle 一致"。执行器实现按"出现贵族选择 UI 则点击对应贵族"分支编写，且必须容忍该 UI 不出现（单贵族自动颁发）。

## E2 >10 宝石返还子流程 ✅（完整实测）

- **操作序列**（实测）：取宝石模式选 3 颗（手 8→11）→ 点"确认拿这些"→ **页面进入"丢弃多余宝石"子模式**
  （提示"等待你丢弃多余宝石（每人最多持有10个）"+"请丢弃 1 个宝石，已选 0 个"）
  → 手中每颗宝石渲染为**独立单位筹码按钮**（`button.ccbs-circle.ccbs-color-{c}`、文本为空、toggle 选中/再点取消，计数文案"已选 N 个"实时更新）
  → 点"确认丢弃"→ 成交、回合流转。
- **关键发现（规则差异）**：**选中"刚拿的颜色"（本次为白）并确认丢弃，被网页接受**。引擎 `generate_return_combos`
  屏蔽刚拿颜色（`splendor_model.py:329-363`），故引擎的 `returned_gems` 组合是网页允许集的**子集**。
- **对执行器的意义**：返还子流程 = "点单位筹码 ×N → 确认丢弃"两步；执行器永远选择引擎动作编码的 `returned_gems`（掩码子集内），无需实现"丢刚拿色"分支。

## E3 终局结算 DOM 🔶

- **实测**：房主点顶部"结束游戏"→ 底部弹"确认结束游戏吗？[取消][确认]"→ 点确认 → **立即返回房间页**（棋盘 DOM 消失、出现"开始游戏"按钮、双方回座位）。
- **结论**：
  1. 强退路径的终局信号 = "棋盘 `.ccbs-card` 消失 + 房间页元素（开始游戏按钮）出现"——可靠、可检测；
  2. 自然终局（有人 ≥15 分打完本轮）的结算画面**待 P3 实战补测**（候选信号同 BROWSER_RL_MAPPING §5.3）；
  3. `browser_env` 的终局检测应以"棋盘消失 / 房间页元素"为兜底信号，与状态文本检测并行。

## E4 空牌库 reserve 是否发金 ⬜

- **不可达原因**：2 人局每层牌库 36/26/16 张，单局（~30 回合）无法清空任何一层；实验设计需要"某层牌库为 0 时预定该层桌面卡"。
- **引擎语义**（备查）：`collected_gems = {"yellow":1} if board.gems["yellow"]>0 else {}`，只看金库不看牌库。
- **计划**：P3 长时间部署中若自然出现（极小概率）则补测；否则维持"以引擎语义为准 + monitor 监控差异"。

## E5 自愿少拿宝石 ✅（全计划最高风险项，已裁决）

- **操作序列**（实测）：手宝石 0（≤7）→ 点"💎取宝石"→ **只点 1 颗白筹码** → "确认拿这些"按钮**未禁用** → 点击 → **成交**
  （手宝石 +1 白，状态切"等待玩家2操作"）。
- **后续多次复现**：每回合只拿 1 颗均被接受（本轮实验中先后 5 次单颗拿取全部成交）。
- **结论**：**网页 = 标准规则（允许拿 1~2 颗）；引擎 = 非标准规则（手 ≤7 强制最少拿 min(3, 可用色数) 个，`splendor_model.py:443-452`）**。
- **影响分析**：引擎掩码 ⊆ 网页合法集。网页上会出现"引擎掩码外的合法动作"（少拿/拿 2 颗），
  agent 永远不会选它们 → 白丢少量机会，但不会选出非法动作。方向安全。

## E6 同色 7 张购卡上限 ⬜

- **不可达原因**：需专门构造同色 7 张已购局面（单局自然达成需要极长回合与特定牌序）。
- **引擎语义**（备查）：同色已购 7 张禁买该色新卡（`splendor_model.py:534`）。
- **计划**：P3 部署期 monitor 观测；若出现"引擎掩码含买卡但网页不可执行"则升级为 bug。

## 额外实测收获（P2 抽取器/执行器的关键工程事实）

以下为实验过程中顺带验证的 DOM 行为，**直接影响 `dom_extractor.py` / `action_executor.py` 的实现正确性**：

1. **供给筹码只在"取宝石"子模式才是 `<button>`**；其余时刻（含我方回合待机）渲染为 `<div>`。
   供给数量查询必须按容器 scoping 或按 `button` 标签限定——**全局查 `.ccbs-circle` 会先命中卡面费用圈**（DOM 序卡面在前），
   本次实测曾在初版抽取脚本上踩中该坑（把卡面费用读成了供给）。
2. **同步快速连点会丢失点击**：一次 js 调用内同步 click 3 颗筹码，实测只成交最后一次（React 重渲染吞掉中间点击）。
   执行器必须**逐颗点击 + 间隔等待**（人类节奏 0.2~0.5s 下限的又一依据）。
3. **取宝石模式的选中反馈**：点中的筹码数量文本实时 -1（"拿起"），并在确认条附近出现"持有"单位筹码（空文本 button）。
4. **丢弃/返还子模式的单位筹码与供给筹码同为 `button.ccbs-circle.ccbs-color-{c}` 家族**（空文本、无 scale 类），
   与供给筹码（有数量文本、take 模式下带 `scale-125`）可区分——执行器需按"文本为空"区分两者。
   **⚠️ 2026-09-11 勘误：该"文本为空"判据不充分，实际必须按容器 scoping。详见文末 bundle 复核 §勘误 1。**
5. **支付药丸 DOM**（多支付购买实测）：购买可多方式支付的卡后，确认条变为
   `请选择支付方式 | [1白1绿1红1黑] [1绿1红1黑1金] [1白1红1黑1金] [1白1绿1黑1金] [1白1绿1红1金] | 取消`，
   **点药丸即成交**。药丸文本格式 `数字+颜色单字` 序列（白/蓝/绿/红/黑/金），`parse_pill` 按此解析。
6. **预留**：点目标卡"预定"按钮即成交，金 +1 自动发放（面板即时更新），无二次确认。
7. **回合状态文本**：`等待你操作` / `等待玩家{座位号}操作` 为叶子节点文本，稳定可查（终局时消失）。
8. **房间页识别**：终局/未开局状态的特征 = 棋盘 `.ccbs-card` 消失 + `开始游戏` 按钮出现。

## 2026-09-11 ccbs bundle 复核（方法变更 + 勘误 + 新增事实）

**方法变更（重要）**：网页是静态 SPA，`https://fe-1255520126.file.myqcloud.com/game/static/js/*.js`
（共 51 个 webpack chunk）即其**完整源码**。把 chunk 全量下载并解码 `\uXXXX` 转义后 grep 真实组件，
可把此前标 `[ASSUMED]` 的选择器/文案**逐条替换为实测值**。
**从此"选择器不确定"的问题先查 bundle，再上网页复核**：bundle 是稳定、可离线、可 diff 的事实源，
而网页实测受房间/身份/时序干扰。bundle 的代价是**版本可能滞后于线上**（详见 §残留风险）。

### 勘误 1：丢弃子流程的单位筹码必须按容器 scoping（推翻「额外实测收获 §4」）

旧结论"丢弃筹码与供给筹码可按**文本为空**区分"**不成立**：取宝石确认条里的"持有"单位筹码
（`div.mt-2.p-2.bg-gray-400`，成交后以 `-mt-12 opacity-0` 隐藏但**仍在 DOM 中**）同样文本为空，
且**在文档序中早于丢弃 UI**。于是未 scoping 的 `button.ccbs-circle.ccbs-color-{c}` 取 `index 0`
命中的是隐藏筹码 → 点击被 React 吞掉 → "已选"恒为 0 → `确认丢弃` 保持 `disabled`，
点它等于空操作。**现场表现正是"确认丢弃按钮点不动"**（2026-09-10 报告）。

- **正确选择器**：丢弃条 `div.space-x-2.p-2.bg-gray-400`（全页唯一同时带这三个类的元素），
  单位筹码 = 该容器内的 `button.ccbs-circle.ccbs-color-{c}`。
- **且必须逐颗按位置点**：同色第 i 颗要点该色第 i 个筹码——同一筹码点两次 = 取消选中。
- **新增离线可验证点**：抽取器把提示文案 `请丢弃 N 个宝石，已选 M 个` 折算成
  `status` 后缀 `；已选M/N`，执行器在点确认前**先校验 M == N**，把"点击没落地"从
  静默空操作升级为响亮失败（回归测试：`test_executor_refuses_discard_confirm_when_chips_missed`
  与 `test_executor_refuses_discard_when_page_asks_for_another_count`）。

### 勘误 2：`确认丢弃` 需要"最内层匹配"规则（click_labelled）

bundle 里的结构是 `<div class="mt-4"><button>确认丢弃</button></div>`——**div 与 button 的
textContent 都是"确认丢弃"，且 div 在文档序中在前**。旧的"取第一个匹配"实现点到的是不可交互的
div，按钮从未被按下。协议层（mock + ego 两个实现）统一加入**最内层匹配过滤**：
只在"不含其它匹配"的元素中取第 `index` 个。副作用：`加入` / `预定` 这类重复纯文本按钮的
`index` 语义**不变**（它们互不包含，全都通过过滤）。

### 勘误 3：回合状态文本是三分支语法，不是两个

```
等待(你|玩家N)操作
等待(你|玩家N)丢弃多余宝石（每人最多持有10个）
等待(你|玩家N)选择要获得的贵族卡
```

末尾可带 `【最后一回合】`。`is_my_turn` 判定改为 `status.startswith("等待你")`——
否则丢弃/贵族子流程期间会被判成"不是我的回合"，使超时救援路径（`force_pass`）选错动作。

### 新增事实：E1 多贵族选择 UI（bundle 判定，module 1364）

- 贵族归属是**动作之后**的性质：动作后满足数 ≥1 才把贵族挂到该动作上；
- 动作后满足数 **= 1** → 网页**自动颁发**，**不出现**选择 UI；
- 动作后满足数 **≥ 2** → 出现选择 UI：每个候选贵族带 `ccbs-candidate` 类，并被
  `<button class="cursor-pointer">` 包裹。**不存在** `.ccbs-noble-options` 容器——该选择器从未生效过；
- 因此执行器必须**按动作后的卡数**重算满足集（镜像引擎 `getLegalActions` 对买卡的后置处理），
  而不是拿动作**前**的 agent 去 `noble_visit`。

**这条同时解释了 2026-09-10 的报错** `noble 3g3r3B is not eligible to visit agent 2`：
旧实现在动作**前**校验归属，于是**每一笔"买卡才凑成贵族"的购买都被自己拒掉**，
哪怕网页本来会静默颁发。回归测试：
`test_buy_creating_noble_eligibility_is_not_rejected`、
`test_two_satisfied_nobles_make_the_executor_pick_the_right_candidate`（两者在旧实现下均失败，
已验证会复现 `noble 4g4r is not eligible to visit agent 0`）。

### 新增事实：贵族候选按 cost 向量定位，而非按序号

候选在页面上的顺序 = 银行顺序，但执行器改为**按 cost 向量匹配**（`_cost_key`，顺序无关）——
贵族 cost 向量全库零重复（既有事实），所以这比"按序号"更稳：页面重排不影响正确性。

### 残留风险与维护约定

- **bundle 版本滞后**：chunk 的 URL 带构建哈希，线上重新发版后旧 chunk 即过期。
  本条事实的有效期 = "下次线上发版前"；**发版后若出现"选择器失效"类报错，第一动作是重下 chunk 复核**。
- **选择器单一存放点**：所有选择器集中在 `dom_extractor.py` / `action_executor.py` / `driver.py` 三处常量，
  改选择器只改这三处，且**改动抽取层后必须跑 `make parity`**。
- **离线夹具已同步**：`fixtures/empty_deck.html`（丢弃条 + 隐藏持有筹码 + `div.mt-4` 确认包裹）、
  `fixtures/noble_available.html`（`ccbs-candidate` + `button.cursor-pointer` 包裹）已按 bundle 结构重写。

## M0.4 规则差异 ADR（决策记录）

**标题**：引擎非标准取宝石/返还规则 vs 网页标准规则——接受差异，训练沿用引擎规则，不加分枝。

**背景**：E5/E2 实测确认网页为标准规则（允许 1~2 颗少拿；允许归还刚拿颜色），引擎为更严格的非标准实现。

**决策**：**接受差异，不改引擎**。理由：

1. **方向安全**：差异方向为"引擎合法集 ⊆ 网页合法集"。策略在引擎掩码内采样，动作在网页端永远可执行；
   两个环境不会出现"本地合法、网页非法"的执行事故（那才是致命方向）。
2. **策略价值影响有限**：被放弃的动作（少拿 1~2 颗、归还刚拿色）是边角优化项；
   对"超越 minimax"的主线目标影响远小于为此引入的复杂度。
3. **单一代码源**：若给引擎加 `standard_take_rules` 开关并启用，训练/评测/奇偶测试三处都要维护两套语义；
   浏览器层打补丁则违反"零规则代码"原则。两害相权，接受差异成本最低。
4. **可逆**：若 P3 落差归因显示"不能少拿"造成可量化的对局劣势（agent 频繁被迫多拿而破坏手牌规划），
   再按 plan/phase-2 §6 的预案加开关（届时 `step(payment=...)` 同样的兼容参数模式可复用）。

**登记的残留风险**：monitor（T2.7）会把"DOM 可点但引擎掩码无此动作"归因为已知规则差异（E5/E2 登记项），
不报 bug；归因白名单需覆盖这两种模式。

## 实测会话纪律（每次实测必读）

1. 自建房间（2 人），第二座位由本人另一身份或挂机座席填充；
2. 每次点击间隔 ≥0.5s，整局时长与人类对局同量级；
3. 实测结束正常离座、离开房间，不留挂机连接（本次实测已执行：双方离座、B 身份标签页关闭）。
