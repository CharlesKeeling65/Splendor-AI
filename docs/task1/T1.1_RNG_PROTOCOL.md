# T1.1 RNG and paired-training protocol

Status: implementation evidence only. This phase does not authorize a model
training run and does not consume validation or sealed-test scenarios.

## Frozen behavior

- `splendor-rng-v1` derives a full SHA-256 digest, a 63-bit library seed, and
  an open-interval 53-bit variate from canonical JSON plus the protocol prefix.
- `treatment_id` is always retained in lineage but never contributes seed
  material. An explicit `coupling_group` is mandatory whenever treatment
  lineage is present; changing that group is the only way to decouple paired
  treatments.
- Scenario source, model initialization, policy action, opponent
  initialization/action, opponent-pool draw, minibatch, and worker streams
  have separate semantic keys. Formal policy and pool sampling use inverse CDF
  against fixed ordering rather than global RNG state.
- Legacy opponents are seeded and restored around both factory construction
  and each decision. The legacy runner API remains unchanged when no lineage
  is supplied.
- A paired schedule is keyed by `(replicate_id, update, game_index)`. Every
  treatment in a replicate must have identical scenario, seat, coupling group,
  and event digests; scenarios cannot repeat within or cross replicates.
- A running schema-v2 manifest must exactly bind the treatment-neutral
  schedule hash, expected treatments, replicate IDs, and worker count.
- `worker_count` means outer concurrency across independent
  treatment/replicate training jobs. Formal multi-worker execution is accepted
  only inside the spawn executor; PPO rollouts within one optimizer remain
  sequential. Results are restored to input order, so future completion order
  is non-semantic.
- Formal Task-1 PPO is restricted to two seats, requires
  `PYTHONHASHSEED=0`, enables deterministic PyTorch settings, and refuses CUDA
  fallback. Checkpoints preserve the effective latest pool CDF, per-update
  counts, and aggregate draw counts.

The protocol known vector is:

```text
key JSON: {"stream_name":"policy_action","update":0}
digest:   2e72c022858541b7b24005eec63c2004b999a77a810949d2d556525b2241b7f1
seed63:   3346948727591223735
u53:      0.6962894161172106
```

## Verification boundary

The T1.1 tests cover canonical derivation, stream isolation, O/A/B/C CRN,
replicate independence, four counterfactual axes, inverse-CDF boundaries,
weighted history buckets, failed-opponent lineage, global-RNG restoration,
minibatch reproducibility, schedule tamper rejection, manifest fail-closed
binding, and a 2-scenario × 2-seat × 2-opponent zero-illegal-action matrix.
Two real O/A formal PPO jobs also run through both one-worker and two-worker
spawn pools; their semantic records, action/minibatch lineage, and final CPU
model tensors must be identical.

T1.1 still uses an isolated source seed to construct the engine board. It does
not claim cross-runner deal identity. T1.2 replaces that temporary boundary
with immutable `ScenarioV1` snapshots and three-runner state/observation/mask
parity.
