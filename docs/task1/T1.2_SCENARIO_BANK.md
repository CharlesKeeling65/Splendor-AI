## 1. ScenarioV1 身份

实现：`policy_imitation/scenario.py`。

`scenario_id == canonical_state_sha256`，哈希输入为 canonical JSON
（UTF-8、key 排序、紧凑分隔符、禁止 NaN），只包含会改变重放语义的字段：

- schema/rule/round limit、2 个座位、当前行动座位与 `action_counter=0`；
- card+noble registry hash、3510 动作的有序 registry hash；
- 3 名贵族的顺序、三层各 4 张明牌的槽位顺序；
- 三层剩余牌堆的完整顺序以及 `deck_top="list_end"`；
- 2p 初始公共宝石与空 agent 状态契约。

以下只作来源/抽样元数据，不进入 state identity：`source_segment`、`source_seed`、
`strata_v1`、`selection_kind`、`inclusion_probability`、`selection_stratum`、
`selection_design_sha256`。
因此，同一开局从不同来源再次出现时仍会被跨 split 去重发现。

固定向量（`ci_smoke:825000`）：

```text
scenario_id          = 4e36c685f742796ba79a02dce1b832e9084feb3f812c760b71937c1c06655e65
card_registry_hash   = 4b392c9f743b992a753d6400ddcce053215545c58c83b07c580186440507cd02
action_registry_hash = 105d4efcf27a258107d3a3c028c7f0ba3fbe4bf924728e2612c6b10b2253fe16
```

装载器使用 `object.__new__` 创建 `SplendorState`/`BoardState`，不先构造再丢弃
随机棋盘；Card、cost dict、noble cost dict 和 agent 容器均逐局新建。生成器调用引擎
自己的初态构造，并只在保存/恢复的局部 Python RNG 状态内播种。Python、NumPy、
Torch 全局 RNG 均由测试锁定为调用前后不变。冻结入口还会逐张核对 source state
中的 card colour/cost/tier/points 与 noble cost，拒绝把被篡改对象按 code 静默
canonicalize。loader 按引擎固定颜色插入顺序重建 gem mapping，因此 source 与恢复态
不仅 legal set 相同，legacy agent 看到的 legal-action 顺序也相同。

## 2. 强制守恒与 registry

每次解析和装载都重新校验：

- 90 张卡恰好出现一次，tier 总量 40/30/20；
- 明牌为 3×4，剩余 deck 为 36/26/16；
- 3 名不重复贵族来自固定 10 名 registry；
- 2p supply 为五色各 4、黄金 5；两个 agent 无卡、无宝石、无贵族、无 trace；
- card/action registry hash 与当前代码一致；
- strata 和 canonical state hash 由内容重算，不信任文件中的声明值。

动作 registry 按 index 编码 enum、宝石映射、card position、noble index；`None`
与空 `{}` 保持不同。任何动作重排都会改变 hash。

## 3. strata_v1 精确定义

所有描述子只读取 12 张初始明牌和 3 名初始贵族，不读取 rollout、胜负或 agent
行为：

| 字段 | 公式 |
|---|---|
| `visible_point_density` | 12 张明牌点数和 / 12 |
| `token_deficit_min/q25/q50/q75` | 空玩家购买每张明牌所缺彩色 token 总数的线性分位数 |
| `cost_colour_entropy_mean` | 每张卡 cost share 的 Shannon entropy / `log(5)`，再对 12 张取均值 |
| `cost_colour_concentration_mean` | 每张卡最大颜色 cost share，再取均值 |
| `noble_pair_weighted_jaccard_mean` | 3 对贵族 cost 向量的 `sum(min)/sum(max)` 均值 |
| `visible_noble_alignment_cosine` | 明牌 bonus-color 计数向量与贵族总需求向量的 cosine |
| `low_cost_high_point_count` | `total_cost <= 7 && points >= 1` 的明牌数 |

删除了恒为零的开局可买性；没有使用未定义的 “rush index”“阻塞难度” 或
“贵族竞速” 标签。

## 5. bank 与 sealed gate

`scenario_bank.py` 把每行写成 canonical JSON，bank identity 是**未压缩 JSONL**
的 SHA-256；`.jsonl.zst` 由单线程 `zstd -19` 编码，压缩字节另有 artifact hash。
文件名含 payload hash，数据和 sidecar 均以 exclusive-create 写入并设为只读；重复
写入不覆盖。

IID bank 的 inclusion probability 固定为 1。平衡压力集要求一个**事先登记的
64 字符十六进制 SHA-256 selection key**，在每个 descriptor bin 内按 keyed SHA-256
lottery rank 取前 `per_bin` 项。由此每个候选的设计 inclusion probability 才是
`per_bin / candidate_bin_count`，而不是把固定排序的 sampling fraction 冒充概率。
bank 同时保存 candidate collection/state-set hash、key、bin edges、各 bin 候选/入选
数与 selection-design hash；每行反向绑定该 design hash。重复候选在抽样前即拒绝。
压力集仍只可作诊断，不能将未加权均值报告为 IID 结果。

T1.4 的训练 bank 是第三种、仅限 `train-schedule` 的
`natural-deal-srswor` 设计：在注册的 200,000 个自然发牌 source seed 有限总体上，
由一次性 root 诱导均匀随机排列并无放回取样。它不是严格 IID，也不允许进入
T1.3 的 `weighting="iid"` 正式评测路径。bank sidecar 保存完整抽样设计 hash、active
replicate 集、总体与样本量，以及 pooled/per-replicate、pooled-seat/per-replicate-seat
四种一阶纳入概率；每行以 design hash 和 replicate stratum 反向绑定。

`scenario_collection_sha256` 对按 scenario identity 排序的逐行 digest 再作 canonical
hash；这样 loader 可逐行验证规范 JSON、source-seed 顺序、每个 ScenarioV1、全 bank
payload/collection/state-set hash，而无需同时持有未压缩 payload。formal spawn worker
使用 subset loader：仍流式核验**整个** bank，但只物化本 job schedule 引用的 scenario，
避免每个 worker 复制 160k–200k 个对象。完整 loader 保留给小型 validation/stress/final
bank。rolled training bank 还必须先经 parent-side `audit_seed_roll_scenario_bank`，把整库
逐行按注册 source seed 重新发牌并与 root allocation 核对；standalone loader 的内容哈希
检查不能替代这个正式 provenance audit。同一 parent gate 还把已验证的 `source_seed`
接回 root allocation，逐坐标核对完整 schedule 的 scenario/seat 顺序；每个 spawned worker
对自己物化的 replicate/treatment subset 再做一次，因此重算 lineage 的 schedule relabel
也会在优化前失败。

普通 loader 无法返回 sealed rows。唯一受支持的读取上下文要求：

1. `purpose == "final_report"`；
2. candidate freeze 文件列出有序且按 digest 去重的 checkpoint SHA-256，并绑定 manifest
   declaration hash；
3. manifest v2 已有 approval event，状态为 `approved` 或 `running`，且其
   `artifact_contract.scenario_banks[logical_split]` 精确等于待开封 bank payload hash；
4. 在读取任何 scenario row **之前**，以文件锁和追加语义写入 `started`；
5. context 退出时追加 `completed` 或 `failed`，事件以 SHA-256 前向链连接；
6. ledger 严格校验事件字段、hash chain、`started → finished` 状态机与全程 binding；
   同一 bank 出现过一次 `started` 后永久拒绝再次消费。

数据文件名也必须逐字等于 `<logical_split>-<payload_sha256>.jsonl[.zst]`；loader
重新编码后要求 payload 恰为 canonical JSONL 且按 source seed 严格递增。因此“改名并
重签 sidecar”与“重排/美化 JSONL 后重签”均失败。

测试 sealed gate 使用已经消费过的历史 `stabilization_test` fixture 段，不触碰新的
`task1_sealed_test_iid`。正式 final N 必须等 T1.3 power analysis 与 T1.4 人工批准后
才冻结；不得在本阶段提前生成并查看。

## 6. runner 接入

- `Game` 新增末尾可选 `prepared_game_rule`；默认构造顺序和 seed 行为不变。
- `evaluation.play_game(..., scenario=...)` 从 snapshot 装载并在记录中保存 scenario
  identity/source；未传 scenario 时仍走历史整数 seed。
- `collect_ppo_game(..., formal_rng=..., scenario=...)` 要求两者同时出现且 identity
  一致；formal 路径不再允许从 lineage seed 现场重发牌。
- formal PPO job 必须提供 bank path，`FormalTrainingSpec` 与 running manifest 同时
  绑定 bank payload SHA-256；schedule 缺 scenario 或 hash 不一致均在优化前拒绝。
  worker 对大 bank 流式全量认证、按本 replicate 的 schedule ID 子集物化。

parity 测试对 `v1` 与 `public-v2` 分别比较 raw rule、`Game` prepared rule、raw
evaluation 首决策 probe 与 PPO 首 transition 的 board identity、observation 和 3510
维 legal mask。
