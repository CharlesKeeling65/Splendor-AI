## 1. 为什么不复用 42 / 1234 / 2024

`42 / 1234 / 2024` 是历史训练标签，不是新 runner 下独立随机抽取的 replicate，继续
使用会把历史选择与本轮方法比较混在一起。新协议把 `replicate_id=0..4` 仅作为区组
地址；实际 model-init seed 由一次性 256-bit root、实验名、阶段和 replicate 域分离
派生。正式路径显式拒绝把三个历史数当 replicate ID，派生出的五个 `seed63` 也不得
与其相等。

生产 roll 已在代码提交、预算和 authority 位置获批后创建一次。当前测试中的全零/
全一 root 只是 known vector，不是候选生产 root。底层构造器允许小规模 CI roll，但其
artifact 明确标记 `design_profile=ci-fixture`；只有阶段名精确为 `T1.4` 且设计精确为
5×32,000 才标记 `task1-formal-5x32000`，优化器也会再次硬性检查，因此 1×2、2×2
等夹具或换名阶段不能被冒充为正式训练。实验/阶段/treatment 标识还必须是去除首尾
空白且不含控制字符的 canonical identifier，`"T1.4 "` 不能借字符串别名绕过 v2 gate。

## 2. 冻结随机化设计

事实总体是注册表中的：

```text
logical split:       train-schedule
source segment:      task1_train_schedule
source range:        [1,150,000, 1,350,000)
population size:     200,000
protocol:            splendor-seed-roll/1
root source:         secrets.token_bytes(32) / OS CSPRNG
selection:           HMAC-SHA256 keyed global permutation, no replacement
allocation:          consecutive 32,000-row blocks in replicate-id order
reserved replicates: 0, 1, 2, 3, 4
pilot replicates:    0, 1, 2
seat assignment:     independent keyed rank, exactly 16,000 / 16,000 per block
```

HMAC message binds protocol, experiment, phase, logical split, source segment/range,
registry hash and source seed. Seat rank uses a separate domain. Adding reserved blocks
does not change earlier blocks: the first three blocks from a five-block plan are exactly
the same as a three-block view. Treatment is not an allocation axis, so `O_bridge` and
`O` in the same replicate consume identical scenarios and seats; this is deliberate CRN,
not duplicate evidence.

This is a randomized finite-population SRSWOR design, not strict IID. Before the root is
drawn, the declared first-order probabilities are:

| scope | scenarios | inclusion probability | seat-specific probability |
|---|---:|---:|---:|
| one replicate | 32,000 | 0.16 | 0.08 |
| three-replicate pilot union | 96,000 | 0.48 | 0.24 |
| all five reserved blocks | 160,000 | 0.80 | 0.40 |

After the root is fixed, a particular source has a realized 0/1 inclusion indicator; the
table describes the pre-randomization design. Row metadata points to the full design and
its replicate stratum. These training rows are never treated as an IID evaluation sample;
`PairedEvaluationSpec` 在构造阶段即拒绝它们，避免先跑局、后到统计阶段才报废。

## 3. One-shot authority and anti-reroll boundary

For one fixed `(experiment_id, phase)` in one approved authority directory:

1. acquire an exclusive file lock;
2. create an identity reservation with `O_EXCL` semantics **before** drawing entropy;
3. write and fsync the root plus its SHA-256 commitment;
4. deterministically reconstruct all five allocations, seats and model-init lineages;
5. publish a content-addressed, read-only canonical JSON artifact;
6. append and fsync one hash-chained `roll-created` authority event.

A retry returns the exact existing roll. A changed design is rejected. A crash before a
valid reservation is complete leaves a blocking record rather than authorizing another
draw; a crash after the reservation resumes from the same root. Concurrent callers are
serialized and publish one event. Loading replays the complete HMAC permutation and checks
reservation/ledger/artifact/manifest hashes rather than trusting stored seed lists.

The authority is a local operational trust boundary, not an external randomness beacon.
Copying or deleting the entire authority directory cannot be detected by local code alone.
Therefore the production authority path and commitment must be reviewed outside the run,
the root must be revealed before outcomes exist, and an alternate authority or root is a
new declaration requiring fresh human approval. File permissions and a hash chain detect
ordinary mutation; they do not claim protection against an administrator who rewrites the
whole filesystem history.

Manifest 审批验证不是只检查嵌入事件“能否自哈希”：它会重新打开声明的绝对
authority 路径，逐项核对 reservation、完整 ledger hash chain、content-addressed
artifact 与 root-derived plan。路径任何一层经过 symlink、artifact 缺失，或伪造一个
内部自洽但不在 ledger 中的事件，都会在审批/装载与运行时重复失败。
首次创建和 existing-roll retry 走同一真实目录校验；不能在创建后把 `artifacts/`
替换成指向外部目录的 symlink 再借 retry 路径读入。
manifest 的 load/write/lifecycle lock 同样先把相对输入固定到 lexical absolute path，
并拒绝 leaf 或 parent-directory symlink；同用户恶意并发替换仍属于下述本地管理员边界。

## 4. Scenario and training bindings

The streaming writer regenerates every selected source through the engine, emits canonical
ScenarioV1 JSONL in ascending source-seed order, and records content/artifact/collection/
state-set/design hashes. It checks exact replicate counts and refuses source, scenario-ID
or state reuse. Formal runtime then replays `source_seed -> ScenarioV1`, requires the exact
root-derived source set for the active replicate, and compares every sorted
`(update, game_index)` row with the root-derived **source order, scenario identity and seat**.
Thus a caller cannot reverse or relabel scenario/seat rows, recompute internally consistent
RNG lineage, and still pass. The full parent-side bank/schedule audit and each worker's subset
gate both perform this comparison before optimizer work.

普通 `load_scenario_bank` 负责 canonical/schema/content-address 验证；正式入口还必须
调用 `audit_seed_roll_scenario_bank`，对**整库**逐行回放 source seed，而不只检查当前
worker 会用到的 subset。

`paired-training-v2` binds all of the following before optimization:

- seed-roll payload, revealed root commitment and authority event;
- full ScenarioV1 bank payload and treatment-neutral paired schedule;
- sorted treatment set, reserved active replicate set and worker count;
- immutable opponent-pool snapshot, including checkpoint file hashes;
- current clean/patch-bound repository provenance and a running manifest v2;
- 每个 treatment 的 BC 初始 checkpoint、完整 PPO/reward config、独立 opponent-pool
  hash；`config.seed=0` 是明确的“未使用”哨兵，真正随机流全部来自 root；
- exact treatment × replicate job matrix and distinct output directories；父进程在 spawn
  前一次性预留所有目录，worker 和低层 trainer 都复核 reservation，重复/改道运行失败；
- `replicate_stage=pilot` 只能精确使用 `(0,1,2)`；`confirmatory-reserve` 只能精确使用
  `(3,4)`，不能把任意 subset 或混合 active set 伪装成同一分析阶段；
- reserve activation 不是一个可随手填写的 64-hex 字符串：独立、只写一次、canonical
  `splendor-confirmatory-activation/1` 文件绑定 completed pilot manifest 的绝对路径、
  文件 hash、declaration hash、completed lifecycle event 与时间，以及实际 pilot evidence
  文件的绝对路径和 hash。新 manifest 的 formal binding 与 artifact contract 同时绑定
  activation 的路径和 hash；审批与 runtime 都重开三份文件，拒绝 symlink、错实验、
  错 replicate、倒置时间或事后篡改。

Activation gate 证明的是“评审者批准的 pilot evidence 字节没有被换掉”，不是由机器
自行判断该 evidence 的科学结论。当前协议要求 evidence 非空并内容寻址；后续 crossed-pilot
driver 必须产出有 schema 的方差/power 报告，评审者负责在 activation 前核对其语义。这是
显式治理边界，不能把一个通过 hash 校验的任意文件自动描述为 pilot 成功。

Legacy `paired-training-v1`, ordinary PPO training, and existing RNG known vectors remain
unchanged，但 `phase=T1.4` 的 formal training 明确禁止回退到 v1。V2 forbids legacy
`training_seeds`; CUDA training must later use
`.venv-p5000`, must see the Quadro P5000, and must fail rather than fall back to CPU.

## 5. Approval and execution boundary

This implementation is not permission to draw the production root. The order is:

1. commit and independently verify the protocol;
2. present the exact experiment ID, authority directory, five-block reservation, active
   pilot subset, treatments, reward contracts, budget, wall-clock/disk caps and GPU guard;
3. obtain explicit approval;
4. draw/reveal exactly one production root and publish its commitment/artifact hashes;
5. materialize only the approved non-sealed training bank and approve the matching
   manifest;
6. run smoke checks, then the approved formal jobs.

No validation or sealed bank is generated by the seed-roll step. Pilot outcomes cannot be
used to redraw, relabel, reorder or replace any of the five reserved source blocks.

## 6. Automated evidence

`tests/test_seed_roll.py` covers fixed vectors, three-to-five block stability, 160,000
unique source allocations, exact seat balance, global-RNG isolation, strict stream axes,
historical-seed rejection, crash/concurrency/idempotency behavior, root/ledger/artifact/
manifest tampering, including the retry-directory symlink attack, streaming bank generation,
source-state replay, root-order schedule relabeling, schedule CRN, T1.4 v1 fallback, running-
manifest binding, and the post-pilot activation evidence chain. Existing RNG, ScenarioV1,
manifest and formal-spawn tests remain part of the compatibility gate.

“流式”指 writer 不保留 160,000 个 `ScenarioV1` 对象；它仍保存 O(K) 的 state/digest
索引，而 200,000 个 source 的 HMAC 排名也是 O(N) 排序。实测完整 5×32,000
allocation 的额外峰值约 56 MiB、约 6.4 秒；正式生成前仍要重新核对内存、磁盘与墙钟
上限。若总体继续扩大，应改为外部排序/增量摘要，不能把当前实现描述成 O(1) memory。
