The production operator interface is the canonical Python module below. It
accepts one JSON declaration and has four public commands. The frozen
`.venv-p5000` predates the optional `task1-pilot` console-script entry, so every
production command uses its exact interpreter plus `-m`:

```bash
PYTHONHASHSEED=0 CUBLAS_WORKSPACE_CONFIG=:4096:8 \
  .venv-p5000/bin/python -m \
  splendor.agents.our_agents.policy_imitation.pilot_orchestrator \
  preflight /absolute/path/to/orchestration.json

PYTHONHASHSEED=0 CUBLAS_WORKSPACE_CONFIG=:4096:8 \
  .venv-p5000/bin/python -m \
  splendor.agents.our_agents.policy_imitation.pilot_orchestrator \
  launch /absolute/path/to/orchestration.json

.venv-p5000/bin/python -m \
  splendor.agents.our_agents.policy_imitation.pilot_orchestrator \
  status /absolute/path/to/orchestration.json

.venv-p5000/bin/python -m \
  splendor.agents.our_agents.policy_imitation.pilot_orchestrator \
  attach /absolute/path/to/orchestration.json

task1-pilot-monitor /absolute/path/to/orchestration.json

task1-pilot-monitor --watch 30 /absolute/path/to/orchestration.json
```

`preflight` is read-only. `launch` first repeats preflight and then starts one
detached tmux supervisor. Before invoking tmux, it publishes a one-shot launch
snapshot and independently passes the original manifest/control/output identity
to the supervisor, so a missing or replaced declaration cannot redirect the
failure lifecycle. `launch` does not trust tmux process creation alone: it
captures early stderr in a one-shot `supervisor.log` and waits up to 30 seconds
for an exact-schema, hash-validated durable `running` handshake. Status v2 binds
the sole tmux pane PID to the supervisor PID, and the matrix PID must be its
direct child and lead its own process group. Any early exit, malformed status,
PID mismatch, timeout, or launch-stage exception blocks the manifest. The
supervisor starts the formal matrix in a separate
process group, polls it every five seconds, and writes
`orchestrator-status.json` beside the declaration. A successful matrix writes
an exclusive `completion.json` containing hashes of every job's initial, best,
final, compact result, status, compressed update journal, checkpoint-selection,
40 nonzero selector checkpoints, and 41 per-checkpoint validation artifacts.
Completion also rechecks the update hash chain, validation evidence chain and selected
checkpoint before transitioning the running manifest to `completed`. A child
failure, failed job status, wall-clock breach, disk breach, or supervisor signal
terminates the matrix process group and transitions the manifest to `blocked`.
Existing output directories are never resumed. `task1-pilot-monitor` is a
strictly read-only view: it reads the declaration/manifest/status and bounded
job summaries, reports aggregate update progress and wall/output/free-space
headroom, and never transitions lifecycle state or parses a multi-gigabyte
legacy result in full. On a claimed terminal success it deliberately
stream-hashes every completion-receipt artifact (including each compressed
journal) before reporting `complete=true`; that final integrity pass may take
longer than a live progress snapshot but uses bounded memory.

## Frozen production gates

- Interpreter and prefix must be exactly `<repo>/.venv-p5000/bin/python` and
  `<repo>/.venv-p5000`.
- `PYTHONHASHSEED=0` must have been set before Python starts;
  `CUBLAS_WORKSPACE_CONFIG` must be `:4096:8` or `:16:8`.
- CUDA must be available, the visible device must end in `Quadro P5000`, its
  compute capability must be `(6, 1)`, and the PyTorch build must advertise
  either the binary-compatible Pascal `sm_60` cubin target or native `sm_61`.
  NVIDIA guarantees same-major cubin compatibility from a lower minor target
  to a higher minor desktop GPU. The production `.venv-p5000` reports `sm_60`;
  a live 265→128→3510 forward/backward smoke test on the `(6,1)` P5000 passed.
  There is no CPU fallback.
- The matrix is exactly treatments `O`, `O_bridge` × replicates `0,1,2`, in
  canonical replicate-major order: six jobs with three spawn workers.
- Every treatment config is the frozen C2-R2 recipe: `public-v2`, 4×128,
  return critic, 2,000 updates × 16 games, `lr=1e-4`, critic `lr=5e-4` with
  two warm-up epochs, `gamma=.99`, GAE `.95`, clip `.2`, entropy `.005`,
  minibatch 256, four epochs, terminal utility 10, target KL `.02`,
  current/history mass 1 and history limit 4. It requests CUDA, uses the
  formal unused `seed=0` sentinel, two seats, and `eval_every=50`. Only shaping
  differs: `O=safe-potential-v1`, `O_bridge=terminal-biased-potential-v1`.
- Both arms use the exact DAgger-2 initializer at
  `runs/policy-imitation/formal-3.3-20260907/bc-dagger-2/best.pth`
  (`e64b722f...1e6f867`) and the source-only unit-weight training pool
  `ga`, `heuristic`, `heuristic-rush`, `heuristic-hoard`, `minimax` in that
  order. Complete PPO config, initializer, and pool hashes are bound by the
  manifest treatment contracts and reconstructed at admission.
- New orchestration-v3 attempts use a 36-hour wall cap so both three-job waves
  can complete with margin; logical output remains capped at 32 GiB and
  remaining filesystem space at at least 40 GiB, before and throughout
execution. Historical orchestration-v2 declarations remain readable and
retain their exact 18-hour cap; they cannot silently inherit the v3 limit.
- Read-only preflight permits a never-launched output root to be absent and
  measures it as zero bytes. After declaration bytes are rechecked, launch
  creates or verifies one empty, real root before tmux starts, rejects symlinked
  parents, and passes its `(st_dev, st_ino)` identity through both internal CLI
  levels; every supervisor and child watchdog then treats disappearance or
  replacement as a hard error.
- Only a non-sealed `train-schedule` natural-deal bank containing exactly the

## Reused protocol gates

The orchestration layer reconstructs the schedule through
`make_seed_rolled_training_schedule`, checks the immutable seed-roll authority
and manifest binding, loads and validates the complete bank, and constructs
`FormalPPOTrainingJob` inputs. Actual execution calls
`run_formal_ppo_training_jobs`, which repeats code/dependency/runtime hashes,
full source-to-ScenarioV1 bank replay, root-derived scenario/seat order, exact
treatment/replicate matrix, checkpoint/config/pool hashes, the content-addressed
validation-A selector and opponent identities, and the one-shot formal output
reservation before any optimizer work.

This entry point never creates a seed roll or bank. It reads only the declared
non-sealed training bank and 10-row validation-A bank; stress, validation-B,
sealed, and reserve rows remain forbidden. The selector bank was separately
materialized and source-replay audited after the implementation commit.
Publishing the final approved manifest and transitioning it to `running` remain
separate, auditable preparation steps.

## First launch attempt and fail-closed recovery

The first production manifest declaration
`645a3eb9f46e5eb7aec6f77b20348057f118809d0491ea9f9153d5240b185096`
and orchestration declaration
`784d0ced6600a75b8b6541133ecd67f022be1abb2cb15ed632d6f81e0f6d1610`
passed the full P5000 activation preflight. `tmux new-session` returned zero,
but the session disappeared before writing `running`; status remained
`launching`, there was no CUDA process, and the formal output tree remained
empty. The operator transitioned that manifest to `blocked`. It is terminal
and must never be resumed.

That event showed that a tmux creation return code alone was not a sufficient
launch receipt, and the vanished pane had no durable early stderr. The retry
implementation therefore added the one-shot log, status-v2 identity parser,
30-second process-tree handshake, and one fail-closed region covering every
step after launch begins. No optimizer update, validation checkpoint result,
training game, validation-B/sealed row, or reserve replicate was produced by
the blocked attempt.

The first hardened retry (`pilot-retry-1`) also passed admission but was
rejected by the new handshake before any output or CUDA process. Its durable
log identified the exact CLI defect: when this module was itself invoked with
`python -m`, the nested supervisor command used runtime `__name__` and therefore
attempted `python -m __main__`. The same construction also affected the matrix
grandchild. Both process commands now use the immutable canonical module name,
with regression tests that force the parent module's runtime name to
`__main__`. The r1 manifest is `blocked` and must not be resumed.

An independent read-only audit then exceeded its assigned scope and executed
the one-shot r2 `prepare` inside its isolated test environment. The resulting
manifest correctly recorded `cuda_available=false`, `cuda_device_count=0`, and
`resolved_device=cpu`. When the host operator attempted activation, the formal
runtime-equality gate rejected that provenance before tmux creation and moved
r2 directly from `running` to terminal `blocked`. R2 has no status, supervisor
log, training directory, optimizer update, or CUDA process. Production
`prepare`, `activate`, and `launch` must therefore be executed only by the host
operator; independent test agents remain strictly read-only and may not
materialize control artifacts.

## R3 terminal evidence and persistence correction

The host-only r3 preparation bound clean commit `f88cf30`, the P5000 CUDA
runtime, the approved seed roll and the two non-sealed banks. Its durable
status-v2 handshake proved the tmux supervisor, matrix child, three spawn
workers and three CUDA contexts were live. This was therefore the first real
formal T1.4 optimizer attempt, not another launch failure.

At the exact 18-hour v2 wall gate, the first wave had durably reached
`r0-O=1432/2000`, `r0-O_bridge=1416/2000`, and `r1-O=1386/2000`; the other three
jobs had not started. The supervisor terminated the process group and moved the
manifest from `running` to terminal `blocked`. The terminal output was
20,686,058,987 bytes with 62,011,502,592 free bytes, so the wall gate—not CUDA,
the output cap, free space, an illegal action, or a training exception—caused
the stop. The partial jobs contain 67,744 completed training games and 5,160
scheduled selector games. Their best validation counts are useful diagnostics
only: best-of-many selection, an incomplete treatment×replicate matrix and the
missing second wave forbid a reward-contract, model-variance, power or
shortlist claim.

Forensic inspection found two avoidable persistence costs. Each update appended
large replay evidence to an in-memory list and then atomically rewrote the whole
pretty-printed `result.json`; the three partial result files reached roughly
2.4–2.5 GB each. The trainer also retained every 2.8 MB update checkpoint,
reaching about 4 GB per active job. Neither artifact was needed at that cadence
for optimizer semantics.

The retry path now makes the following formal-v2-only changes; legacy and
paired-training-v1 outputs keep their established inline-log behavior:

- Each update is one canonical, hash-chained, independently compressed zstd
  frame in `updates.jsonl.zst`. Appends are inode-bound, no-follow, fsync'd and
  strictly numbered `0..N`; completion streams and revalidates canonical JSON,
  chain hashes, formal coordinates, terminal game accounting and the compressed
  artifact hash. `result.json` is now a bounded schema-v2 summary binding the
  journal, aggregate opponent usage, selector and phase timings.
- Production preflight requires the host `zstd` executable before any launch
  mutation; absence therefore fails admission instead of failing a worker.
- Transient `update-N.pth` files are pruned after each update. The live
  four-checkpoint history window and every validation milestone are retained;
  completion keeps all nonzero `0/50/.../2000` selector checkpoints plus
  `initial.pth`, `best.pth` and `final.pth`.
- Status-v2 separates rollout, optimizer, checkpoint, validation,
  validation-evidence, selection, pruning and journal time. A supervisor stop
  now stamps manifest-bound live children `interrupted` and unstarted reserved
  children `not-started`, without overwriting completed/failed evidence or
  following symlinks.
- The monitor has a stdlib-only top-level launcher, avoiding the eager Torch
  imports of the training package. Against the retained 20.69 GB r3 tree, a
  one-shot snapshot completed in 0.16 seconds with about 36 MB peak RSS while
  reading only bounded edges of the three multi-gigabyte legacy results.

A deliberately conservative local persistence microbenchmark used 101 frames
whose canonical payload was 1,242,017 bytes per entry. The new path averaged
0.0505 seconds per fsync'd append and 312,234 compressed bytes per entry
(31,535,611 bytes total). This synthetic payload compresses less than a sampled
r3 record region, so it is used only as a resource-envelope check, not a model
throughput claim. Even that conservative ratio projects the six journals below
3.8 GB rather than six multi-gigabyte cumulative result files; milestone
validation/checkpoint artifacts remain under the unchanged 32 GiB output and
40 GiB free-space gates. Because the six jobs execute in two three-worker waves,
orchestration schema v3 independently binds a 36-hour wall cap. Schema v2 stays
loadable with 18 hours for historical audit and can never acquire the new cap by
code upgrade.
