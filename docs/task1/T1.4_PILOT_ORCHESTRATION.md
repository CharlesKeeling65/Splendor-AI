# T1.4 crossed-pilot production orchestration

Status: implementation and CI-fixture tests complete. The explicitly authorized
non-sealed 96,000-row pilot bank, 10-row checkpoint-selector bank, and baseline
validation-A/stress banks are materialized and audited. The 1,800-game frozen
baseline and fixed-model variance decomposition are complete; see
[`T1.4_BASELINE_RESULTS.md`](T1.4_BASELINE_RESULTS.md). **The final pilot
manifest and CUDA/P5000 production training have not yet run**.

The operator entry point is `task1-pilot`.  It accepts one JSON declaration and
has four public commands:

```bash
PYTHONHASHSEED=0 CUBLAS_WORKSPACE_CONFIG=:4096:8 \
  .venv-p5000/bin/python -m \
  splendor.agents.our_agents.policy_imitation.pilot_orchestrator \
  preflight /absolute/path/to/orchestration.json

PYTHONHASHSEED=0 CUBLAS_WORKSPACE_CONFIG=:4096:8 \
  .venv-p5000/bin/python -m \
  splendor.agents.our_agents.policy_imitation.pilot_orchestrator \
  launch /absolute/path/to/orchestration.json

.venv-p5000/bin/task1-pilot status /absolute/path/to/orchestration.json
.venv-p5000/bin/task1-pilot attach /absolute/path/to/orchestration.json
```

`preflight` is read-only. `launch` first repeats preflight and then starts one
detached tmux supervisor. Before invoking tmux, it publishes a one-shot launch
snapshot and independently passes the original manifest/control/output identity
to the supervisor, so a missing or replaced declaration cannot redirect the
failure lifecycle. The supervisor starts the formal matrix in a separate
process group, polls it every five seconds, and writes
`orchestrator-status.json` beside the declaration. A successful matrix writes
an exclusive `completion.json` containing hashes of every job's initial, best,
final, result, status, checkpoint-selection, and 41 per-checkpoint validation
artifacts. Completion also rechecks the validation evidence chain and selected
checkpoint before transitioning the running manifest to `completed`. A child
failure, failed job status, wall-clock breach, disk breach, or supervisor signal
terminates the matrix process group and transitions the manifest to `blocked`.
Existing output directories are never resumed.

## Frozen production gates

- Interpreter and prefix must be exactly `<repo>/.venv-p5000/bin/python` and
  `<repo>/.venv-p5000`.
- `PYTHONHASHSEED=0` must have been set before Python starts;
  `CUBLAS_WORKSPACE_CONFIG` must be `:4096:8` or `:16:8`.
- CUDA must be available, the visible device must end in `Quadro P5000`, its
  compute capability must be `(6, 1)`, and the PyTorch build must advertise
  either the binary-compatible Pascal `sm_60` cubin target or native `sm_61`.
  NVIDIA guarantees same-major cubin compatibility from a lower minor target
  to a higher minor desktop GPU. The production `.venv-p5000` reports `sm_60`;
  a live 265→128→3510 forward/backward smoke test on the `(6,1)` P5000 passed.
  There is no CPU fallback.
- The matrix is exactly treatments `O`, `O_bridge` × replicates `0,1,2`, in
  canonical replicate-major order: six jobs with three spawn workers.
- Every treatment config is the frozen C2-R2 recipe: `public-v2`, 4×128,
  return critic, 2,000 updates × 16 games, `lr=1e-4`, critic `lr=5e-4` with
  two warm-up epochs, `gamma=.99`, GAE `.95`, clip `.2`, entropy `.005`,
  minibatch 256, four epochs, terminal utility 10, target KL `.02`,
  current/history mass 1 and history limit 4. It requests CUDA, uses the
  formal unused `seed=0` sentinel, two seats, and `eval_every=50`. Only shaping
  differs: `O=safe-potential-v1`, `O_bridge=terminal-biased-potential-v1`.
- Both arms use the exact DAgger-2 initializer at
  `runs/policy-imitation/formal-3.3-20260907/bc-dagger-2/best.pth`
  (`e64b722f...1e6f867`) and the source-only unit-weight training pool
  `ga`, `heuristic`, `heuristic-rush`, `heuristic-hoard`, `minimax` in that
  order. Complete PPO config, initializer, and pool hashes are bound by the
  manifest treatment contracts and reconstructed at admission.
- Wall time is fixed at 18 hours, logical output size at most 32 GiB, and
  remaining filesystem space at at least 40 GiB, both before and throughout
  execution.
- Only a non-sealed `train-schedule` natural-deal bank containing exactly the
  pilot replicates and 96,000 rows is accepted. A bank containing reserved
  replicates 3/4, a validation bank, stress bank, or sealed bank is rejected.
- The selector bank is the first 10 registered validation-A seeds
  `1372000..1372009`, payload SHA-256
  `88981246ab82552da43f158dc67d7969622ab5fe3354f24cfb7d49eaf9cb8626`,
  artifact SHA-256
  `f63ecdb8fd8837147f467da939065235dbb936e6cd1893cebed1ed5527b86830`,
  and state-set SHA-256
  `2f820a2b8e78bd76e2afa6ec1d19c416373a9b0d5e9a24dedaf68969e7b2d2b4`.
- Checkpoint selection is part of the trainer contract: update 0 and every 50th
  update through 2000 are evaluated on the first 10 registered validation-A
  ScenarioV1 openings, both seats, against the frozen source-only `ga`,
  `heuristic`, and `minimax` opponents (60 scheduled games). `best.pth` is the
  checkpoint with the largest integer win count; an exact tie keeps the earlier
  update. Integer-seed validation and sealed data are rejected.

the temporary artifact if validation fails.

## Reused protocol gates

The orchestration layer reconstructs the schedule through
`make_seed_rolled_training_schedule`, checks the immutable seed-roll authority
and manifest binding, loads and validates the complete bank, and constructs
`FormalPPOTrainingJob` inputs. Actual execution calls
`run_formal_ppo_training_jobs`, which repeats code/dependency/runtime hashes,
full source-to-ScenarioV1 bank replay, root-derived scenario/seat order, exact
treatment/replicate matrix, checkpoint/config/pool hashes, the content-addressed
validation-A selector and opponent identities, and the one-shot formal output
reservation before any optimizer work.

This entry point never creates a seed roll or bank. It reads only the declared
non-sealed training bank and 10-row validation-A bank; stress, validation-B,
sealed, and reserve rows remain forbidden. The selector bank was separately
materialized and source-replay audited after the implementation commit.
Publishing the final approved manifest and transitioning it to `running` remain
separate, auditable preparation steps.
